## 2. 产品目标与明确取舍

正常使用只有四步：**开始并建报告 → 展示/选择调用链 → 主 Agent 评审 → 提交并落盘**。

优先级：报告可靠交付、多链人工选择、范围与证据诚实、常见 B 端问题有用、执行开销可控。

| 方案 | 取舍 |
|---|---|
| 继续给 1.6.7 增加门禁与提示词 | 不采用；模型仍需组织大量有顺序依赖的调用 |
| 整体回退 1.4 | 不采用；会重新带入安装、导航等已修问题，且旧版也不能证明模型必然完成 |
| 复用现有导航/安装，重做窄的 Review 主路径 | 采用；以 1.4 展示体验为参考，减少身份和阶段协议 |

这是一项明确的产品约束变更：1.8 普通 Review 不再要求 Certified ChangeAnalysis、ReviewUnit、RuleDispatch、Certified Findings 或 Reviewer session attestation 才能生成评审报告。保留的机器检查是输入结构、实际文件/引用、用户选择、范围及保存结果。**机器定位核验不能证明业务问题一定成立**；报告表达 AI 评审结论，待确认项单列。

不做持久索引、调用图数据库、后台任务、自动恢复平台、业务知识接入、TeamAI 新功能、日志查询、自动修复或新的安装系统。原有 Test/Fix/Apply/DB/Upgrade 边界不借本次重写。Review 永不自动修改生产/测试代码。

## 3. 入口、范围和停止边界

正式入口保留 `/harness-review [Class|Class.method|file]`，在主会话执行，`subtask: false`。宿主命令模板先执行常量 Runtime `review start`，成功创建报告后才交给模型解释目标；用户参数只作为文本传入，不拼到 shell 命令。自然语言 `harness review ...` 必须路由到同一入口；无法确定性路由的宿主不能宣称支持该别名，显示正式命令即可。

为了避免静默改变原有变更评审语义，1.8 默认仍是**变更评审**：无目标时检查当前 Change Set；有类/方法/文件目标时检查相关变更及必要上下文。指定目标没有相关变更时明确告知，可由用户明确改为“检查当前实现”；不自动切换成历史全量审计。当前实现模式仅在用户明确要求后使用，报告单列模式且不声称问题由本次变更引入。

当前实现模式是同一评审流程的范围选项，不另建分析系统。未支持的语言/动态关系直接列出限制，不伪造覆盖。

- 读取用户指定类/方法或当前变更，沿实际调用关系补充 Service/实现、Mapper/SQL 和相关配置。
- 到 RPC、MQ、缓存客户端、第三方 SDK、JDK/Spring 框架边界停止；存在获准本地依赖源码也只作为明确需要的只读上下文。
- 不根据一个字段名猜实际 Bean；重载、多个实现、反射及动态 SQL 无法确认的部分标记为未解析。
- 单文件 AST 批处理，同 run 相同内容结果复用；扫描前后检查内容变化，变化后不复用旧定位。
- 默认单次导航子进程超时 30 秒、准备范围累计工具预算 120 秒；超限停止扩展并列出缺口，不偷偷截断后宣称完整。不把模型等待计入 AST 指标。
- 不设置“到第 N 层就算完整”。循环调用通过已访问的精确引用停止；预算截断属于未完成范围。

## 4. 多调用链人工选择

链以用户可理解的业务入口编号展示，不自动将共享 Service 的不同入口折叠成一条来规避选择。V1/V2 可以提示共用核心代码，但默认仍展示独立入口。

- 0 条：区分“确实没有相关内部链”和“发现失败/未完成”。前者可按已声明文件范围评审，后者只能输出未完成记录或等待用户明确缩小范围。
- 1 条：仅在本次目标的发现已完成、没有可能改变选项的未解析分支时自动继续。
- 2 条及以上：展示完整编号、业务名、代码路径、涉及文件及缺口；结束当前助手回合，等待**下一条真实用户回复**。
- 用户可选单条、多条或明确“全部”；空白、“继续”、“好的”、模型自行生成的 ALL 不授权选链。
- 同一个 Controller 内的多条方法链同样适用，不以类名输入当成全部链批准。
- 选择绑定本 run、本次菜单摘要和当时文件内容；菜单/源码变化使旧选择失效。必要时重新展示变化后的菜单。
- 发现不完整时不得把“全部可见链”表述为“全部实际链”。用户可以明确接受有缺口的限定范围；报告仍标注 PARTIAL。

选择验证集中在 Host 选择适配器。复用现有 `reviewauthority/primary.go` 的真实下一用户回合判断，提取与 Finding/analysis attestation 无关的部分。输入由受支持 Host 的实际消息记录与执行上下文提供，不能接受模型参数中的 `userConfirmed: true`、伪造 role 或菜单副本作为身份依据。

基准实现可使用已验证的原生 OpenCode 本地 export 读取真实菜单与后续 user 消息，但只用于需要人工选择的动作，使用一次有界读取；不再要求一个正在运行的选择工具先有“已完成提交”的 attestation。使用参数数组启动原生进程，opaque sessionId 不解释格式。若 Host 无法提供真实回合，停在等待选择并保留报告，不退化为模型代选。该边界不是防御同 OS 用户恶意改文件的安全沙箱。

## 5. 最小 Runtime / Host 接口

不把八阶段 Runtime 换成另一套八阶段 Runtime。新增局部 `internal/reviewrun` 模块隔离 1.8 普通 Review；旧协议保留给历史 run/非本轮功能，不混用证据。

用户不手填 runId。入口分配随机 runId 与明确报告路径；Host 通过同一次命令上下文绑定，禁止全局“取最新 run”。不同会话、项目和并发 run 互不覆盖。

| 动作 | 输入与职责 | 输出 |
|---|---|---|
| `review start` | 无目标参数，创建本次目录与未完成报告 | runId、reportPath、execution=INCOMPLETE |
| `codea-review.prepare` | runId、明确 intent；按需读取/发现，必要时消费主 Agent 对已有候选的补充解释并核验引用 | 菜单/已选范围、缺口、reportPath |
| `codea-review.select` | runId、当前 optionsHash、选择 ID；从真实 Host 消息核对用户选择 | 已选范围或 HUMAN_SELECTION_REQUIRED |
| `codea-review.finish` | runId、读取记录、问题及待确认风险；一次调用完成校验、保存、渲染、回读 | execution、reviewConclusion、reportPath、reportSha256 |
| `codea-review.status` / `cancel` | 本 run；status 只读核对文件，cancel 明确记录用户取消 | 当前结果与同一 reportPath |

上述工具统一由 `.code-harness/tools/codea-review.ts` 暴露，以 action 区分，结构化参数直接提交；新路径不使用旧 `codea-reviewer-submit`。prepare/finish 是工具内部 Runtime 调用，Agent 不再手写多个 JSON 传输文件或调 `certify`、`units`、`dispatch`、`report review`。

保留少量运行条件：范围未准备、等待选择、可以提交、已取消。`execution` 是 INCOMPLETE / COMPLETE / CANCELLED，`reviewConclusion` 是 BLOCKING / ACTION_REQUIRED / NO_ISSUES_FOUND / UNDETERMINED，`coverage` 是 COMPLETE / PARTIAL；三者分开，禁止把进程成功映射为代码通过。

结论计算固定：未完成/取消或 coverage=PARTIAL 时为 UNDETERMINED，同时保留已定位问题；完整评审含 CRITICAL/HIGH 为 BLOCKING，仅含 MEDIUM/LOW 或待确认风险为 ACTION_REQUIRED，全部为空才是 NO_ISSUES_FOUND。这些是模板的评审分级，不授予上线批准。用户选择子集后，该子集可 COMPLETE，但报告始终显示全局未评审范围。

默认工具预算适用于 Runtime 工作，不应在等待人工选择时计时失败。两条以上已确认链必须等待人工；若发现缺口可能改变菜单，先披露缺口，用户接受限定范围后才能就该明确范围继续选择。

链结构只有一个 `nodes[]`：每个节点同时包含 path、symbol、role，workspace 默认为 current；取消平行 `chain[]` / `chainRefs[]`。精确引用不唯一时保留候选，不猜位置。候选链含“已确认连接”和“未解析连接”，不能只证明节点存在便声明调用成立。

最小持久文件：`run.json`（目标、选项、用户选择、已读内容标识、最近错误）、`result.json`（finish 接受的结构化结果）、`review.md`（用户报告）。源码正文不复制成多层证书，不创建 Reviewer authority 文件。已有 runs/chains 用户数据保留。

## 6. 报告保证及故障语义

### 6.1 入口先写文件

start 只有在 `.code-harness/runs/<runId>/review.md` 写入并回读成功后才返回 READY。初始报告明确“评审未完成，尚无评审结论”，显示时间、项目与报告路径；目标尚未解析时写“尚未确定”，不能编造。

磁盘不可写、空间不足、目录冲突时不能承诺文件存在：入口立即返回具体路径与系统错误，不继续消耗模型分析成本。

### 6.2 正常完成只有一次提交

finish 先校验全部输入，再保存 result，生成完整 Markdown，在同目录临时文件写入并使用经 Windows 验证的原子替换，最后回读核对内容。失败保留旧的未完成报告/上一份有效报告，并返回可操作错误；不得提前返回 COMPLETE。

`review.md` 是用户可见完成标志。其末尾非展示元数据保存 schemaVersion、runId、execution、resultSha256；status/finish 重试核对 result.json 的摘要和报告内容。run.json 不另存一个能单独宣称完成的布尔值。JSON 已保存而报告替换前崩溃时仍是未完成；同内容 finish 重试补齐报告，不开启新 run。保存机制局限于单 run，不引入通用事务框架。

输入结构/定位错误在原 run 修正，保持原范围和用户选择；内容确实变化才要求重新准备/选择。已完成 run 的相同 finish 幂等返回已有报告；不同结果拒绝覆盖，需新 run。

单 run 的写操作使用互斥锁并检测已有完成报告，避免两个同时到达的 finish 相互覆盖；锁只保护本地短暂读写，不覆盖模型等待或人工选择。源码不是在入口冻结后永远不变：prepare/读取时记录内容 hash，finish 检查同一批实际文件，改变则明确要求刷新该范围。

模型自然语言里说“完成”不影响 Runtime 状态。模型提前结束或被强杀而未调用 finish，最少保留入口创建的未完成报告；不声称能在宿主退出后继续执行或自动补齐语义。明确 cancel 可以写取消原因；未收到退出事件时只能保留“未完成”，不能猜取消时间。

部分已读代码存在有效发现时允许生成**未完成的评审记录**，保留有效证据与缺口；这种文档不能通过正常成功验收。已知尚需人工选择且未选择的链，不得执行 Finding Review 或输出其正式发现。

### 6.3 内容校验

finish 检查路径属于当前选定范围、行号存在、引用片段与本轮读取的文件内容匹配；变化返回 SOURCE_CHANGED 并保留报告。问题需要描述、影响、建议和实际证据；没有证据的判断只能列为待确认风险。没有发现时明确“在声明范围内未发现需处理问题”，不写“系统绝对安全”或“允许上线”。缺少覆盖、工具超时与引用未解析不等价于零问题。

用户选择的 scope 外文件不能混入问题清单；依赖仓只读上下文不扩展本仓授权。`introducedByChange` 只在变更模式且有 diff 证据时成立，当前实现模式不得伪造引入时间。

源码/项目文档中的指令属于待评审数据，不能改变工具权限、选择或报告完成条件。显示内容需转义 Markdown 表格/链接/HTML，不执行源码中的脚本或远程资源。

## 7. 报告结构与视觉规范

主产物是 UTF-8 无 BOM 的固定模板 Markdown，不新增 PDF/浏览器服务。报告默认中文；源码标识符保留原文，工具日志不占首屏。

1. **评审摘要**：项目/需求（缺失则标未提供）、时间、模式、目标、执行状态、评审结论、范围/文件数、各风险数量、1–3 条核心发现、建议动作。
2. **调用链与覆盖范围**：每条链先业务名、再角色与真实符号；已选/未选分开；展示外部边界与未解析项。长链仍完整保留，不因首屏排版静默截断。
3. **风险清单**：编号、严重度、摘要、业务影响、建议动作，按严重度与稳定路径排序。待确认风险单独列出，不计入已确认问题数量。
4. **问题明细**：问题/触发条件、业务影响、代码位置、最小代码证据、建议、验证场景。范围外、纯风格问题不进入正式列表。
5. **后续处理与评审边界**：具体待办、未覆盖部分、依赖限制；尾部给出版本、提交号和技术追溯。不编造负责人、期限、事故金额、通过率或节省时间。

执行完成与风险结论分别显示。严重度不是上线审批，AI 建议不冒充负责人的批准。汇总数量从接受的结构化问题计算，不由模型另写一套数字。

统一使用少量状态图标、简短标题、固定表格和留白；颜色不能成为唯一含义。Markdown 表格不堆长代码，问题明细用 fenced code；路径链接使用安全相对路径，不能把 Windows 冒号路径误识别为 URL。生成后由工具返回绝对可定位的 reportPath。

## 9. 验收与发布门槛

验收分四层，不混淆名称：

1. **组件/故障测试**：上述 H01–H17 与报告 golden；含有问题、无问题、未完成、取消、选择等待、不可写、替换失败。
2. **原生 Windows 集成**：正式包里的真实 Go Runtime、ast-grep 与 OpenCode；固定模型响应仅验证传输、真实回合判断和文件机制。
3. **真实模型自主评审**：用常见 Controller→Service→Mapper/XML 小项目，种入权限隔离/事务或 SQL 等有明确证据的问题，以及干净对照；模型自行调用准备、选择后继续、finish。测试驱动只发正常用户输入与明确选择、观察轨迹/文件；禁止提供工具调用脚本、预制 findings 或补调 Runtime finish/report。至少单链有问题、单链无问题、多链选子集三类各 3 次独立 fresh run 全部产出有效正式报告；另测提前结束只能留下未完成文件。
4. **实际内网验收**：用户部署的真实私有模型和 Windows 包重复上述三类核心流程。无法访问该环境时只报告第 1–3 层结果，内网一项标未验证，不把公共/fixture 模型结果替代。公开 CI 可先产待验收候选包，但正式“可用并完成交付”的声明必须具备该层证据。

正常样本必须工具返回 COMPLETE、review.md 存在且非初始占位、摘要/选中范围/问题明细正确、没有未声明缺口；只创建空报告不算通过。问题召回至少覆盖种入的高风险案例，不用零 findings 来换取链路成功。

性能记录分别给出模型等待、导航、读文件、校验/渲染、总耗时和子进程数量。标准本地小 fixture（10 个 Java 文件内、单条链）Windows 准备/导航合计目标 ≤15 秒、finish 本地校验/写盘 ≤5 秒；工具耗时超目标要定位，不靠放宽到 20 分钟验收。真实模型总耗时先实测，不以固定响应耗时宣传性能。

完整 `go test -count=1 ./...`、`go vet ./...` 必须 fresh PASS，真实 Windows 包和升级 PASS。测试不能跳过相关失败，当前报告流程删除的旧约束测试逐条说明替换理由，历史版本兼容测试保留。禁止拿旧 exact HEAD 的绿色 run 作为新代码验收。

发布证据至少记录产品 exact HEAD、Run ID、Job ID、包 SHA256、模型/provider/Host 版本、场景、真实工具轨迹、报告路径与 hash、预期/实际问题、人工选择消息对应关系、耗时及未验证项。日志脱敏，不把公司源码或凭据上传公网。

## 10. 安装与兼容

继续 Windows 10/11 x64、OpenCode、完全离线运行。不新增 npm/bun 在线安装、HTTP 模型客户端、容器、WSL 或后台服务。沿用既有已批准 Go 模块与 ast-grep；CI Go 1.23.12、原生 OpenCode 1.18.25 是当前验证工具点，内网实际 Host 版本另记录。

## 11. 研发顺序

T1 先完成最小 run 和真实报告写盘；T2 完成有界范围/多链真实用户选择；T3 接主 Agent 的单次 finish 与实际模型小闭环；T4 完成汇报模板和历史故障回归；T5 完成离线升级、最终 Windows 与真实模型/内网验收。

先证明正常用户入口可以真正产报告，再扩充场景。每任务测试通过后单独交付验收，不跨任务宣称完成；T3 的自主执行未通过时停止扩充，不继续建设周边能力掩盖主路径故障。
