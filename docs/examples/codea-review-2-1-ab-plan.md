# Codea Review 2.1｜A/B 测试安排（P2，尚未执行）

> **计划，不是实测结果。** P0 CLI 与项目知识库已由用户在内网确认；P1 KB Reviewer 真实工具轨迹与知识归属须先验收。后续由真实 Windows / OpenCode / 私有模型执行。

## 实验的唯一主要变量

- A：同一冻结 Codea Review 2.0，输入 `/codea-review`。
- B：新增 KB Reviewer，输入 `/codea-review-kb`；唯一预期增量是主动调用 TeamAI 项目知识。
- 两组使用完全相同的模型 ID/配置、温度（如可控）、项目/HEAD、staged/unstaged/untracked 文件、重要系统提示、Java Skill、报告模板及工具授权流程。每次新开会话，交换 A/B 运行顺序，以减少时序影响。
- 检查 TeamAI 是否已由全局/项目规则或 SessionStart Hook 自动注入知识：若存在，只可声称“B 主动 Recall 相对现有环境的效果”，不可声称 A 完全不含知识。
- 测试期间不要修改业务 Git 变更；业务仓库中已有的 `temp/` 报告不参与 Git 业务审查。

## 测试范围一致性：SQL-only 与 TeamAI 增益必须分开验收

**当前 2.0 保持冻结，而 2.1 KB 新增独立 `.sql` 有效文件覆盖**。因此当输入包含 standalone `.sql` 变更时，A/B 差异不只来自 TeamAI：**不得将 B 新发现的 SQL 风险直接归因为知识增强收益**。

- **纯知识增益 A/B**：使用两组**共同覆盖的 Java/Mapper XML 代码**和完全相同的 Git 快照，验证相同的通用问题能否被保留，以及 TeamAI 是否带来额外的项目专属真实风险。比较的前提还包括相同代码文件清单、模型、授权和基础 Skill。
- **独立 SQL 覆盖回归**：另在 KB 入口单独测试 SQL-only committed/staged/unstaged/untracked；验证隐藏目录和根 temp 双排除、生效 SQL 风险审查、误报与五章报告。不纳入 16 次“TeamAI 净收益”的计数，除非将来原版 2.0 也明确支持独立 SQL 取证后再重新设计可比实验。
- **三个历史通用 Finding 固定回归**：先取得真实内网原版 Review 报告与代码快照，人工提取三条已确认问题的唯一标识/位置/触发条件（不在公开仓库上传业务源码）。KB 版对相同 Java Diff 必须保持三项通用问题发现能力；模型每次运行有随机性，单轮遗漏不能仅靠一次修订宣称已经消除，需要逐条真实对比和失败归因。
- 任何通用 Finding 消失，先检查 G 通用风险检查完整性与上下文取证，再检查 K 是否因为命中/补查导致审查视野收窄；不能把“TeamAI 查不到知识”当作通用问题消失的理由。

## 四类场景 × 两组各两次 = 16 次

| 场景 | 人工先定真实结论（不向模型提供） | A × 2 | B × 2 | 重点 |
| --- | --- | --- | --- | --- |
| S1 通用 Java 风险非退步 | 同一 Java/Mapper XML 快照中人工确认的通用风险；如有真实历史三项 Finding 则逐项比对 | 待执行 | 待执行 | B 不能因知识检索遗漏原版已有的真实通用 Finding |
| S2 项目专属业务规则 | 订单结算中不允许直接取消；**同一代码变更另含重复取消/重复库存释放等多个候选问题**，便于核验知识复用和必要补查 | 待执行 | 待执行 | B 发现有项目依据的真实风险，且同场景多个问题不重复 Recall |
| S3 合法实现 | 满足现行规范并有等效保护 | 待执行 | 待执行 | B 不引入误报 |
| S4 项目冲突规则 | 两个已绑定 TeamAI 项目的不同业务约束 | 待执行 | 待执行 | B 不跨项目引用专属规则 |

每轮提前由人工保存**脱离给模型的 Ground Truth**（期望问题、业务规则、排除反证、允许知识作用域、版本时间）；样本代码注释和用户 Prompt 不能提示正确答案。P2 结果必须是私有模型实际输出，而非编写的示意 Finding。

## 每次运行必填记录

| 字段 | 样例/填写约束 |
| --- | --- |
| 场景/组/序号 | S2-B-1 |
| 日期与顺序 | 真实时间与先 A 后 B/先 B 后 A |
| Git 快照 | 基线 ref、HEAD SHA、staged/unstaged/untracked 的内容哈希；两组要相同 |
| 模型与 OpenCode 版本 | exact ID/版本，温度与工具策略 |
| TeamAI 作用域 | 活动项目 ID 列表、项目知识路径、是否已预注入 |
| 查询轨迹 | 原生 Shell 命令、是否经 ask、Recall 尝试次数（包括失败）、每次查询词、每次候选≤3、来源/命中/采用结果 |
| 检索策略 | 实质行为变更场景数、纳入检索计划的场景、实际覆盖场景、逐候选 KB_REQUIRED / KB_USEFUL / KB_NOT_NEEDED 分类 | 
| 知识复用与补查 | 哪些候选问题复用同一知识、补查的必要性、因预算未覆盖哪些场景 | 
| 结果 | TP/FP/FN（逐个缺陷）、严重误报、有效来源/适用规则/代码证据是否成立 |
| 性能 | 纯模型+工具耗时、授权等待、总耗时（秒） |
| 故障 | 知识召回失败、来源模糊、回退是否成功 |
| 报告归档 | 单独的 Markdown 文件路径 + 脱敏 OpenCode TUI 轨迹 |

## 归档防覆盖（测试人员人工操作，非 Reviewer 新功能）

两组 Reviewer 都保留冻结的固定报告路径：`temp/codea-review-report.md`。**每执行一次都应立即复制**到本地受保护的归档位置再运行下一组，例如在 Windows PowerShell：

```powershell
New-Item -ItemType Directory -Force -Path ".\temp\ab" | Out-Null
Copy-Item -LiteralPath ".\temp\codea-review-report.md" -Destination ".\temp\ab\S2-A-1.md"
# 另一次执行 /codea-review-kb 之后：
Copy-Item -LiteralPath ".\temp\codea-review-report.md" -Destination ".\temp\ab\S2-B-1.md"
```

根据实际场景改文件名；保存每轮经过脱敏的工具调用轨迹。归档在项目根目录 `temp/` 下，它被已有 Git 文件筛选排除。**不要把内网知识正文/未脱敏项目源码提交到公开 GitHub。**


## 新增的检索策略评价指标

以下指标均**依据真实工具轨迹和人工 Ground Truth**计算，不以模型自行宣称“已完成知识核验”为准。

| 指标 | 计算或观察方式 | 主要风险 |
| --- | --- | --- |
| 应检索场景覆盖率 | 实际检索的不同应检索业务场景数 / 经人工确认应检索场景数 | 模型没发现 Bug 就不检索 |
| 召回知识相关率 | 与业务直接相关、项目来源允许的候选知识数 / 所有候选数 | 空泛或其他项目知识 |
| 单次 Recall 候选规模 | 每次实际用于分析的候选文档数 ≤3 | 上下文污染 |
| 知识复用率 | 同一业务多个候选问题使用同一已有规则的情况，及不必要的重复 Recall 次数 | 每 Finding 单独查询 |
| Finding 知识核验覆盖率 | KB_REQUIRED 候选中完成有效规则核验的数量 / KB_REQUIRED 候选总数 | 未验证就宣布业务规则违规 |
| 补查必要性 | 每次第 2～4 次 Recall 是否有新场景/新关键约束/可消歧例外 | 无意义检索拖慢 |
| 查询预算遵守率 | 每轮 TeamAI Recall 尝试数 ≤4（含失败/拒绝）；默认目标≤2 | 频繁授权、延时 |
| 代码证据有效性 | Finding 关联本次 Git 变更且排除等效保护的比例 | 只凭知识推断 Bug |
| 新增真实业务风险 | B 比 A 多发现的 TP，必须证实依赖相关项目规范 | 模型随机性误判为知识收益 |
| 误报、漏报和耗时 | 与 A 对照 FP/FN，模型/工具/授权等待分拆记录 | 收益抵不过成本 |

特别注意：`KB_NOT_NEEDED`（例如通用事务异常吞没）**不能因 TeamAI 没命中而降低确认度**；`KB_REQUIRED` 没有足够有效知识时属于待确认，不算 TP。预算不足需在报告边界里记录未覆盖的业务场景，不是 Java 代码未审查。

## P1 → P2 的前置条件（实际执行）

先在 Windows 内网依 `codea-review/KB-README.md` 完成 T1～T10，记录真实工具轨迹并给独立审核：T2 不先发现 Bug 仍主动 Recall；T3/T4 知识复用；T5/T10 多场景优先且 ≤4；T7 回退正常；T8/T9 不误用知识。上述证据未通过前，**不能因为静态测试通过就宣布 2.1 已经提升风险发现能力**。

## 第一轮判定

- **收益**：B 在至少一个项目专属规则案例中相对 A 增加真实、有效、有源可查的 Finding。
- **质量**：不因 TeamAI 引入严重误报、跨项目知识错用；S1 通用风险召回不得明显下降。
- **可靠性**：TeamAI 失败可回退基础审查，报告完整，权限没有被绕过。
- **性能**：以额外耗时约 ≤30% 为优化目标（非第一轮硬门槛），测量授权次数、各阶段时长。
- **实验强度**：16 次是探索性小样本；偶然一次多发现不能证明稳定改善，结果波动明显时扩充案例。
- **发布**：仅在 P2 实测成立后另行决定是否默认启用；本次 P1 保留两个独立入口、原版行为不变。
