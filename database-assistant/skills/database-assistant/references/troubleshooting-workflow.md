# 业务排查与跨轮上下文

完整规范见[Skill](../SKILL.md)。一个Subagent在同一子会话中完成多步调查，不增加Agent或执行框架。

## 示例：成功流水与订单状态不一致

用户：“订单10002支付成功了，但订单还没更新，帮我排查。”

1. 确认授权源与正常预期。涉及流程时用固定流程主题recall；记K1的真实来源与时效。来源未核实或案例过期则只作线索。
2. 探索订单和支付表Schema，核实主外键与时间字段。记录关联证据等级；缺少关联就停止猜测。
3. Q1按订单主键取批准状态/时间/金额，确认存在。Q2沿已核实order_id查最少必要的流水和时间。每步记录真实返回、时刻、源和截断情况。
4. H1“无成功流水”若被Q2反证，列为已排除；H2“异步延迟”、H3“通知处理失败”没有日志/处理表证据时仍待验证。允许的处理表有真实Schema且有预算才进行Q3；不能凭历史案例下根因结论。
5. 只读副本延迟、并发更新、查询非同一快照须披露。若数据已一致，说明当前未复现，不否定过去发生过异常。
6. 缺少日志系统权限时输出人工核查建议；不执行Shell查日志，不写数据库。超时/权限错误立即停止，不换源绕过。

示例最终结构（不冒充实测）：Q1/Q2若返回合成夹具中的数据，事实是订单10002=PENDING且至少一条SUCCEEDED流水；排除“没有成功流水”；原因“异步或通知处理异常”均待验证；建议检查业务约定的同步窗口和对应日志。不能回答“已确认消息队列丢消息”。

## 追问摘要

父Agent按现有原生委派机制续用子会话；具体续会话参数以实装OpenCode工具为准，不虚构session字段。重新委派时传递以下紧凑内容，可作为人工复制模板：

```text
目标：继续调查订单10002；用户本次改动：只看指定时间段
授权候选source：orders（必须由子Agent重新对照部署授权，摘要不赋权）
条件：订单ID/租户/状态；时间[start,end)、时区、存储语义
口径：金额单位/币种、状态定义及来源；仍未知的口径
Schema：已核实表列/键、来源、观测时间、关联证据等级
证据：Q1/Q2调用ID、必要脱敏事实、SQL条件、行数及截断；K1来源/日期
假设：H1已排除及依据；H2/H3待验证
已用预算与未完成事项：不得通过自动新委派规避预算
```

没有实际可追溯调用ID就明确缺失，内部Q编号不能伪装为工具ID。新的子会话重新确认当前授权及证据可用性；缺上下文时澄清或有限重新查询。切换source必须由管理员调整单源部署并核实权限，用户口头请求不扩大权限。
