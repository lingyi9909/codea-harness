# 业务排查与跨轮上下文

完整规范见[Skill](../SKILL.md)。一个Subagent在同一子会话中完成多步调查，不增加Agent或执行框架。

## 阶段流程优先级

排查首先经过Agent/Skill实际加载的A→B→C→D→E→F：订单号仍属于业务标识，**先TeamAI定位**业务所属项目/source/候选表与状态流程，然后只在当前授权source核实Schema、形成Q1/Q2条件计划，最后逐条查询。若TeamAI未命中且无法确认业务映射，不从订单号猜表，也不执行查询。下文合成示例以业务定位已经成功为前提；对应预期顺序参见[统一业务SOP](business-sop.md)。

## 示例：成功流水与订单状态不一致

**同源前提：** 仅当`orders`表和`payments`表都实际属于当前授权DBHub source，且相关字段/关联键已核实并获准访问，才可以执行下述Q1/Q2。DBHub模板中的`orders`/`payments`两个source不是可直接关联的两张表。

用户：“订单10002支付成功了，但订单还没更新，帮我排查。”

1. A识别订单异常与正常预期。B先选用已批准固定主题执行TeamAI业务/项目/source/表/流程定位，记K1的真实来源与时效；找不到映射且无法独立确认授权源/表时止于B，不猜测库表。
2. C先核对候选source与系统唯一授权source，再用search_objects探索订单和支付表Schema，核实主外键与时间字段。记录关联证据等级；缺少关联就停止猜测。D在执行SQL前列出Q1主体、Q2支付及后续可选Q3的证据目标与进入条件。
3. Q1按订单主键取批准状态/时间/金额，确认存在。**仅在同源前提成立时**，Q2沿已核实order_id查最少必要的流水和时间。若支付流水在另一个source，Q2不执行，也不尝试其工具或跨库SQL。每步记录真实返回、时刻、源和截断情况。
4. H1“无成功流水”若被Q2反证，列为已排除；H2“异步延迟”、H3“通知处理失败”没有日志/处理表证据时仍待验证。允许的处理表有真实Schema且有预算才进行Q3；不能凭历史案例下根因结论。
5. 只读副本延迟、并发更新、查询非同一快照须披露。若数据已一致，说明当前未复现，不否定过去发生过异常。
6. 缺少日志系统权限时输出人工核查建议；不执行Shell查日志，不写数据库。超时/权限错误立即停止，不换源绕过。

示例最终结构（不冒充实测）：Q1/Q2若返回合成夹具中的数据，事实是订单10002=PENDING且至少一条SUCCEEDED流水；排除“没有成功流水”；原因“异步或通知处理异常”均待验证；建议检查业务约定的同步窗口和对应日志。不能回答“已确认消息队列丢消息”。

## 跨源场景的安全停止示例

当前Subagent仅获准访问`orders`源，支付流水仅存在于另一`payments`源时：

- 已核实事实：Q1显示订单10002在本源为PENDING（附实际调用ID、过滤/执行时间和截断情况）。
- 缺失证据：没有获得另一source的支付流水、支付状态、时间及关联键证据；不能排除“未支付”，也不能确认“通知失败”。
- 人工下一步：由管理员分别审查并配置目标源的只读账号、精确action、数据范围；业务/DBA在独立获准的环境分源核对并提供脱敏结果，核实关联和时间口径。V1.0不自动换源、不生成跨源JOIN、不继承旧源权限。

以上为假设性输出，不代表本轮实际查询。

## 追问摘要

父Agent按现有原生委派机制续用子会话；具体续会话参数以实装OpenCode工具为准，不虚构session字段。重新委派时传递以下紧凑内容，可作为人工复制模板：

```text
目标：继续调查订单10002；用户本次改动：只看指定时间段
授权候选source：orders（必须由子Agent重新对照部署授权，摘要不赋权）
条件：订单ID/租户/状态；时间[start,end)、时区、存储语义
口径：金额单位/币种、状态定义及来源；仍未知的口径
Schema：已核实表列/键、来源、观测时间、关联证据等级
证据：Q1/Q2调用ID、必要脱敏事实、SQL条件、行数及截断；K1来源/日期
假设：H1已排除及依据；H2/H3待验证
已用预算与未完成事项：不得通过自动新委派规避预算
```

没有实际可追溯调用ID就明确缺失，内部Q编号不能伪装为工具ID。新的子会话重新确认当前授权及证据可用性；缺上下文时澄清或有限重新查询。切换source必须由管理员调整单源部署并核实权限，用户口头请求不扩大权限。
