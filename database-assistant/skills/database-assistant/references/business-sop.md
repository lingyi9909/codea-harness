# Database Assistant V1.0｜统一业务执行工作流

> 运行必需规则以已加载的 Agent 与 [SKILL.md](../SKILL.md) 第0节为准。本文件仅供安装、审核和内网测试人员阅读；不需要给Agent开放read权限。原生提示词SOP不等于程序级状态机。

## 阶段门禁与跳过条件

| 阶段 | 必要输入 | 必需动作及通过条件 | 无法满足时 |
|---|---|---|---|
| A 识别 | 用户目标/ID/筛选 | 判断BIZ还是TECH，明确用户要核实的事实 | 缺关键过滤/目标时最小澄清 |
| B TeamAI定位 | BIZ，或需要业务口径的请求 | 在首次DBHub前真实执行获准固定recall；K记录项目、source、表、关系、规则及真实出处，区分候选/未核实 | 未知source/表则停止；已明确授权source/表可转技术事实降级，不给业务结论 |
| C source+Schema | 所有数据库任务 | 先比对系统唯一授权source，再search_objects核验表、列、键、类型和关系；可复用同环境有效Schema证据 | 跨源/权限不符/表名过期则停止或限定本源 |
| D 查询计划 | 每次execute_sql前 | 只列目标、证据Q顺序、下一步条件、预算；不写未经Schema核验的SQL | 条件/口径/成本不清，澄清/退出 |
| E 执行与核证 | 已完成C和D | 单条安全SELECT，实际返回后记录Q和决定下一步 | 空行、超时、无权限分别处理，禁止猜测或绕过 |
| F 结论 | 所有请求，包括失败 | 中文输出K/Q来源、可证实事实、排除与待验证、限制、人工下一步、真实阶段轨迹 | 不虚构调用和项目 |

TECH跳过B的严格条件：用户明确提出系统已批准source及目标表/字段、所求仅为结构或技术数据，且无未知业务指标/状态/归属含义。仅提供订单号并不满足。Schema探索请求可在C后直接F（D/E不适用），但所有SQL查询必须有D。

## 典型工具轨迹（仅预期顺序，不是实测）

| 场景 | 预期调用顺序与输出边界 |
|---|---|
| S01 只有业务名称 | A→B 选批准的业务定位固定recall(K1)→若定位到本源与表，C search_objects→D→E execute_sql(Q1)→F；未定位则止于B，不盲扫 |
| S02 只有订单号 | A(BIZ)→B recall业务/项目映射(K1)→C核验授权source与表→D按ID查主体→E Q1→F；不因ID看似简单而先查Schema |
| S03 知识中表名过期 | A→B K1旧表→C search_objects发现不符→标知识失效；有批准主题和预算可有限重新定位，否则止于C；不执行旧SQL |
| S04 知识找不到业务库 | A→B K1无匹配/未核实→F缺少项目/source/表映射与人工补充；不调用DBHub，不试遍库 |
| S05 业务涉及多个sources | A→B获候选两源→C只确认当前唯一获准源→D/E仅处理获准单源部分（如足够）→F本源事实+另一源待核对证据与人工独立授权；不跨源JOIN/自动换源 |
| S06 纯技术查询但状态需解释 | 若用户先明确唯一授权source/表且只查值：A(TECH)→C→D→E Q1→F技术值；随后要求解释状态：A(BIZ)→B K1状态口径→必要时C复核→F解释或注明语义未知；不凭列名判成功 |
| S07 查询后追问 | A检查原K/Schema/Q及授权是否仍适用→若有效可复用，不重复recall；若业务或源变化先B→C→D→E Q2→F；不能继承旧source权限 |
| S08 TeamAI失败或无关 | A(BIZ)→B CLI拒绝/无关→若source与表仍未知，直接F说明定位不可用；若管理员已授权且用户明确表，可C→D→E仅给技术事实→F不得作业务根因判断 |

## 同源订单支付示例

**成功路径（仅假设性合成数据）：**
用户：“订单10002支付成功，但是订单状态没更新？”
1. A：确定需验证订单当前状态、支付流水及正常更新窗口，属于BIZ。
2. B：用批准的流程/业务映射主题查询TeamAI，记录K1业务项目、当前源及两张表的候选映射、状态规则和来源；不能定位则按缺口停止。
3. C：检查两张表是否确实属于系统唯一获准source，使用search_objects核对order_id、status、时间字段、索引及一对多关系。若分源则仅处理本源事实。
4. D：计划Q1按订单ID查主体；Q1有记录且支付表获准才Q2查关联流水；必要且有权限、预算才Q3查允许的处理表；每一步规定证据目标。
5. E：Q1与Q2由真实execute_sql按顺序返回后，分开确认“订单PENDING”“至少一笔成功流水”；仍不能把状态差异当成通知故障。
6. F：列K/Q真实来源、执行条件、已证实事实、排除的假设、仍需日志证据和建议；仅示例，不冒充实测。

**降级路径：** B无法定位本业务、或C发现旧字段/未授权source时，停止相关SQL；输出止于B/C、已有K或Schema证据、缺失的授权映射/口径以及人工下一步。

## 审核重点

- BIZ任务的调用轨迹应显示 TeamAI recall 早于任何 DBHub search_objects/execute_sql（可追溯K复用须有实际旧证据）；TECH须有满足跳过条件的记录。
- 对SQL任务，执行轨迹必须显示来源授权及Schema已核实、D计划先于execute_sql。不得凭自然语言自述当作工具执行证据。
- 检查source隔离、精确shell白名单、四主题或管理员批准的静态业务主题、SQL只读及超时停止行为均未变化。
- 八个S场景预期均为待内网验证；没有实测结果不得写PASS。
