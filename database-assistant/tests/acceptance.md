## T1 隔离库执行顺序
1. DBA 用隔离的合成数据建 orders/payments，并为两个 DBHub 源分别准备受限只读账号和脱敏视图。不要用生产表测试。记录授权快照、角色、版本、来源与文件 hash。
2. 在开放给 Agent 之前由测试人员验证只读账号直接写入/跨库/原敏感字段/FILE/EXECUTE 均拒绝。再经 DBHub readonly 验证相同攻击，确认数据未变。两层证据分别保存。
3. 导出实际注册工具和生效动作。为 orders 生成候选配置；分别尝试 payments search_objects/execute_sql、未知工具、shell、read敏感文件、edit、子委派，应在工具执行前拒绝。再通过 orders 工具传入跨库 SQL，必须在 DB 层拒绝。
4. 用 database-entry 委派完成普通查询，再故意让父 Agent 直接调用 DBHub：必须拒绝。对现有 Build/其他 Agent 和其他 MCP 实例做绕过检查；存在路径则隔离配置，不以子 Agent 权限作为全局保证。
5. 复测工具列表变化、source ID重复、项目配置覆盖、保存授权覆盖、同名Skill覆盖；一旦权限有效范围变化即重新验收。

## T13 服务端终止与取消失败（仅隔离环境）
- 固定实际 DBHub/mysql2/MySQL 版本及 lockfile；核对 #384/#386 和后续 timeout 实现，不用版本字符串代替行为证据。
- 将隔离源 query_timeout 设短（如3秒）。由测试人员通过直接 DBHub 测试会话发起确定性超时查询（可用 SELECT SLEEP(8) 作历史回归，但另测真实只读计算查询）；不通过生产 Agent 放行资源攻击函数。
- DBA 独立观察该查询线程ID、启动/结束时间及 PROCESSLIST；Agent/客户端必须收到明确错误。必须在自然完成前看到服务端语句终止，不能以客户端返回证明终止。
- 检查超时连接是否被丢弃，未知状态连接不能复用；紧接普通 SELECT 1 必须成功，记录连接生命周期，不仅比较最终值。
- 在隔离网络故障/取消权限故障下制造取消失败，观察服务端是否残留及错误/告警是否明确；不允许报告正常完成。残留由 DBA 清理，停止测试源，不接生产。
- timeout取消不可靠、无服务端证据、缺少池状态证据任一成立，T1不通过。不得进入T2或用CONDITIONAL PASS放行。
